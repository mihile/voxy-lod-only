# 다중 플레이어 탐험 성능 분석 — 0.9 개발판

2026-10-16. 실서버는 읽기 전용으로 참조했다. 설정/JAR/월드 변경,
실서버 재시작, 자동 생성 재활성화 및 배포는 수행하지 않는다.
검증용 개발판이며 실서버에 설치하지 않았다.

## 기준과 장애 원인

- 작업 시작 소스: `8d8bbe0`, 수정 사항 없음, 버전 `0.8.0+1.20.1`.
- 당시 설치 JAR: SHA-256 `0bd108194d4eec0eac0470be0f86040f79f3d1313f83b71c5f26ad7d3af1b247`.
  이를 `build/performance-20261016/baseline-0.8.0.jar`에 읽기 전용 복사해 비교한다.
- 작업 시작 로컬 재빌드 JAR은 `18244e...`로 해시가 달랐다. 클래스 37개 중
  바이트가 다른 4개의 `javap -c -p` 결과는 일치한다. Minecraft 이름이 재매핑된
  sources JAR을 named 소스와 단순 텍스트 비교하는 방법은 사용하지 않는다.
- 현재 실서버 파일의 자동 반경은 32였다. 장애 자료의 반경 128과 구분하며,
  격리 비교에는 장애 당시의 128/32타일/2배치/자동 작업자 설정을 사용한다.

진단 자료에서 확인된 직접 장애는 6GiB 힙 포화와 Full GC 정지다. 약 97%의
전체 힙, 약 99%의 old 영역, 약 7초 동안 Full GC 7회, GC 작업자 중심의 CPU,
최대 36.729초 지연과 두 곳의 Java heap space 오류가 근거다. 전송용 배열이나
구조물 NBT에서 할당에 실패했다는 사실은 그 객체가 메모리를 유지한 원인이라는
증거가 아니다. 원래 장애의 힙 덤프가 없으므로 누수/주요 유지 객체는 미확정이다.

일반 청크 생성도 두 플레이어의 새 지역 탐험에서 CPU와 힙을 사용한다.
LOD Only는 별도 노이즈·구조물·조명 생성, 변환 및 추가 Voxy 데이터 공급을 한다.
VoxyServer의 일반 청크 수집과 전송은 LOD Only를 꺼도 남는다. 세 비용을 합쳐
전부 LOD Only의 누수나 단순한 비행 부하로 설명하지 않는다.

## 다중 플레이어 가설 판정

| 가설 | 0.8 소스에서 확인한 동작 |
| --- | --- |
| 플레이어가 서로 작업을 계속 취소함 | 확인되지 않음. 전역 작업 하나의 소유자를 유지한다. |
| 한 플레이어가 독점함 | 확인. 반경 128은 최대 66,049개 후보이고, 그 영역 완료/소유자 무효화까지 다음 플레이어 차례가 오지 않는다. |
| 취소 작업이 무제한 중첩됨 | 확인되지 않음. 기존에도 취소 플래그와 이전 작업 배출 장벽이 있다. |
| 겹친 범위가 동시에 중복 출력됨 | 전역 소유자 하나와 서로 겹치지 않는 타일 순회, 완료 기록이 이미 일부 방지한다. 실행 중 예약 키는 없었다. |
| 두 플레이어 사이의 거대한 사각형 생성 | 확인되지 않음. 원래부터 한 소유자의 정사각형이다. |
| 플레이어 수만큼 LOD 작업자/배치 증가 | 확인되지 않음. 원래도 전역 8작업자/2배치이다. 두 번째 플레이어는 일반 생성 부하를 추가한다. |
| 오래된 중심점 유지 | 확인. 플레이어가 옛 반경 밖으로 나가기 전까지 큰 옛 영역을 계속 처리할 수 있다. 무제한 요청 큐와는 다르다. |
| 실제 생성 중인 청크와 경쟁 | 가능 경로 확인. 기존 skip은 완료/로드된 청크와 저장 NBT를 확인하며, 플레이어에게 요청된 아직 미완료 FULL 청크는 구분하지 않는다. |

32타일은 출력 1,024청크뿐 아니라 초기 최대 54×54=2,916 ProtoChunk와
38×38 terrain 문맥을 포함한다. 완료 후 맵을 비우는 코드는 이미 있었으므로,
이를 새로 발견한 완료 후 halo 누수로 보고하지 않는다. 생성 중 문맥, 완료 출력과
조명, 다음 생성, 최대 16개 변환 결과 및 저장/전송이 겹치는 순간 비용이 문제다.

0.8의 틱 제한은 제출과 commit 앞에서 반환한다. 이미 실행 중인 배경 생성은
그 틱 제한을 보지 않는다. 전체 배치는 두 개로 유한하지만, commit이 멈춘 동안
큰 결과와 진행 중 문맥을 유지해 GC 압박을 악화시킬 수 있다.

## 변경 설계

- 생성/NBT 읽기/완료 출력/변환/취소 배출을 포함해 전역 슬롯 하나만 사용한다.
  플레이어마다 생성 파이프라인을 만들지 않는다.
- 플레이어 세션별 지연 순회 커서를 보관하고 한 타일씩 round-robin으로 선택한다.
  연결 객체·차원·반경 변경을 추적한다. 8청크 이동 시 대기 커서만 새 중심으로
  교체한다. 여전히 유효한 실행 타일은 낭비하지 않고 마치되, 옛 커서에 속한 타일은
  20초/16청크 경계에서 무효화한다. 두 플레이어 사이의 공간을 채우지 않는다.
- 예약 키는 차원/청크/structures 모드이며, 취소 후 작업과 변환 lease가 끝날 때까지
  유지한다. 완료 기록과 실제 청크를 계속 확인한다.
- 실제 view distance+2 안은 일반 청크에 맡긴다. 해당 범위가 실행 중 출력을 모두
  따라잡으면 private 작업을 취소한다. halo나 구조물 표현을 잘라내는 방식은 아니다.
- 자동 작업자는 접속 중 최대 2, 빈 서버 최대 4이다. 이미 실행된 유휴 단계가
  접속 직후 즉시 OS 수준에서 선점된다고 보장하지 않으며, 경계에서 양보/배출한다.
- 타일 기본값 8, 유지 배치 기본값 1. 예전 JSON의 타일 32/배치 2를 읽어도,
  접속 중 타일 최대 8 및 전역 배치 1이라는 안전 상한을 적용한다.
  빈 서버는 최대 16이며 예약 예산에 맞지 않으면 더 작아진다.
- `resourceBudgetMiB=192`는 halo/출력에 대한 보수적인 예약 추정이다.
  기본 유효 타일 8의 최대 생성 그리드는 900개, 출력은 64청크이다.
  이는 외부 모드의 구조물 캐시·Voxy 저장/전송까지 포함한 정확한 힙 바이트 상한이 아니다.
- 전체 사용량의 정상적인 young GC 파형을 old 점유와 구분한다. 최대 힙 대비 G1 old 사용량이
  82% 또는 힙 여유 96MiB 미만이면 중단한다. 메모리 중지는 old 76% 이하와
  여유 256MiB 이상으로 회복돼야 해제된다. 여유 192MiB 미만은 별도 할당 압력이다.
- 틱/실제 청크 준비/저장 압력을 함께 확인한다. 회복에는 낮은 틱 수치와 건강한
  1초가 필요하다. 지속 압력은 2초 뒤 작업을 배출·재계획한다. 서버 heartbeat가
  멈추어도 배경 작업은 청크 경계에서 양보하고 3초 뒤 중단할 수 있다.
- `maxGenerationStepsPerSecond=512`는 생성 단계/청크 경계의 전역 페이싱이다.
  `maxChunksPerSecond`와 별개다. 후자는 commit 시작 간격이며 0은 개발판에서
  접속 중 8, 빈 서버 32청크/초의 기본 제한이다.
- 서버 틱에 새 sleep/작업 대기를 넣지 않는다. 백그라운드만 짧게 park한다.
  일시 중지보다 먼저 취소 완료와 변환 참조 해제를 처리한다. 기존의 종료 시
  저장 엔진보다 먼저 작업을 배출하는 순서는 유지한다.
- 취소/예외 시 private 맵을 finally에서 비우고, 변환 close는 대기 future 참조를
  비운다. 생성 단계 일부 제출이 실패해도 이미 제출한 형제 작업을 배출한다.
- 일반 청크 방문 이력은 현재 예약 출력에만 유지한다. 완료 파일 형식, 구조물
  모드별 무효화 규칙과 기존 LOD 저장 형식은 바꾸지 않는다.

`status`는 소유자/요청 나이/플레이어별 선택 차례, 압력 원인과 old·전체 힙,
예약/생성 그리드/완료 출력/변환/실행·대기 작업 수, 취소/중복/실제 수요 skip을 표시한다.

## 비교 방법과 한계

`run_flight.py`, `flight_client.py`, 독립된 flight 검증 모드를 사용한다.
실제 loopback 플레이어 연결과 일반 청크 추적을 사용하며, VoxyServer protocol 2
세션/빈 manifest/데이터 수신/ACK를 수행한다. 전체 클라이언트 렌더러는 실행하지 않는다.
폐기용 계정은 creative/flying 상태에서 위치 패킷으로 경로를 따른다. 실제 생존 모드의
탈것·몹 처리 비용을 동일하게 재현한 테스트는 아니다.

- 실서버와 같은 시드와 읽기 전용 모드·설정 snapshot에서 각각 별도 월드를 만든다.
  모든 새 지역 실행은 동일한 spawn-only 월드와 초기 Voxy 캐시를 복사한다.
  기존 지역 비교는 공통 off 비행 완료 월드를 먼저 닫은 뒤 세 버전에 동일 복사한다.
  실서버와 테스트의 `WorldGenSettings` 전체와 데이터팩 선택 64개가 일치함도 확인했다.
  `build/performance-20261016/environment-match.json`에 비교 증거를 남겼다.
- 초당 8블록, 높이 180, 같은 좌표 경로를 사용한다. 사용자가 알려준 말 정도의 속도와
  서로 다른 방향이라는 조건의 고정 근사이다. 원래 경로/탈것 종류는 확보하지 못했다.
  A는 (16384,16384)에서 +X, 분리 조건의 B는 (-16384,16384)에서 -X이다.
  동행 조건의 B는 A에서 Z 방향 64블록 떨어져 같은 +X 경로를 간다.
- 테스트 계정만 모드팩 도입 퀘스트 완료 상태로 준비한다. 실제 차원이 오버월드인지
  확인한 뒤 측정하며, 잘못된 차원/접속 준비 실패 실행은 비교에서 제외한다.
- 실서버에 간섭할 수 있는 CrashAssistant만 테스트 snapshot에서 제외한다.
  다른 원본 모드의 해시 목록과 모든 실행의 JAR/힙/시드는 raw metadata에 남긴다.
- 6GiB `-Xms6G -Xmx6G`, GraalVM 25, G1, 16 논리 CPU 조건이다.
  함께 실행되는 사용자의 원래 프로세스를 종료하거나 설정하지 않는다.
  원래 장애 당시의 호스트 전체 메모리/클라이언트 부하는 재현하지 못했다.
  예를 들어 수정본 120초 분리 비행의 호스트 가용 메모리 최저는 약 12.0GiB였다.
- 틱 관측은 직전 완료 틱을 사용하므로 시작 명령 전/부분 틱이 섞이는 첫 두 관측을
  모든 버전에서 동일하게 제외한다. 그 값도 `leading_partial_tick_max`로 별도 보존한다.
- 재접속의 초기 관측기는 오프라인 시간을 일부 청크 지연에 포함할 수 있었다.
  해당 세 실행은 최종 비교에서 제외하고, 세션별 관측을 접속 종료/차원 변경 시
  정리하는 `probeVersion=2`로 꺼짐/0.8/개발판을 다시 비교했다.
- 실제 청크 지연은 플레이어 주변 3×3 FULL 준비를 추가 생성 요청 없이 관측한다.
  완료 전에 관측 범위를 떠난 probe는 별도 미완료 관측 수이며 엔진 큐 길이와 다르다.
- 이동 중 처리량은 5초 간격의 첫/마지막 status 차이이다. 마지막 5초 및 이후의
  정지 상태 재개 검사·종료 배출을 포함한 전체 처리량으로 부풀리지 않는다.
  `discardedChunks`는 준비된 출력에서 버린 청크이며, 생성 중 포기한 모든 CPU 작업량은 아니다.
- CPU는 Java 스레드 이름별 표본 차이이다. Worker-Main에는 모드가 개입한 일반 생성도
  포함된다. GC 작업자 CPU 자체를 Java ThreadMXBean으로 정확히 귀속하지 않는다.
- 수신 데이터/정확성 검사와 렌더링/FPS·실제 탈것 물리는 구분한다. 짧은 격리 비교는

527.78ms였다. 직전 04:19:53의 LOD 상태는 이미 모든 작업·참조가 0이었다.
종료 때의 공유 캐시/정리 비용까지 해결됐다고 주장하지 않는다. 정확한 보유 객체와
추가 세 회의 원인 귀속은 미확정이다. Minecraft의 틱 작업 시간은 틱 사이의 GC 정지를
모두 담지 않을 수 있으므로 최대 틱 수치와 GC pause를 함께 읽어야 한다.

### 공정성·취소·재개

- 120초 분리 비행에서 양쪽 실행 소유자가 모두 관측됐고, 두 세션의 현재 커서에서
  각각 최대 5번의 타일 선택이 기록됐다. 5분 실행은 각각 최대 7번이었다.
  이 수치는 이동 시 교체되는 커서별 최댓값이며 전체 선택 횟수의 합은 아니다.
- 동행은 두 플레이어 각각 최대 6타일 선택을 기록했다. 5초 간격으로 잡힌 실제 실행
  소유자는 한 명뿐이었다. 공유 범위/빈 타일과 표본 간격을 고려해 CPU 시간이 정확히
  반반이었다고 주장하지 않는다. 분리 조건과 round-robin 단위 검사를 함께 근거로 삼는다.
- 출력 중복 예약 키는 차원/좌표/structures이다. 현재는 전역 슬롯 하나라 동시에
  중복 출력 작업이 실행될 수 없다. 실제 비행의 예약 경합 skip은 0이었다.
  정확성에 필요한 halo 계산을 완료 출력과 혼동해 제거하지 않았다.
- 수정본 여섯 실행 모두 종료 요청 뒤 3초를 기다린 검사에서 `inFlight`,
  `conversionTasks`, `generationGridChunks`, `queuedStageTasks`, `activeStageTasks`,
  `reservedChunks`, `readyOutputChunks`가 0이고 `error=none`이었다.
- 접속자를 둔 채 비행 후 30초 정지 검사에서도 LOD 완료가 추가로 늘었다.
  120초 분리 49/한 명 48/동행 57/기존 지역 48/5분 분리 24/재접속 60청크였다.

  차원 변경이 해당 플레이어만 무효화하는 검사와 요청 교체·배출 회귀 검사를 통과했다.
